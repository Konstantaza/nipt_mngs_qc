# nipt_mngs_qc 1.10.0: как фактически работает pipeline и что показала проверка Samovar

**Подробный исследовательский отчёт · версия 2 · 18 ноября 2026 года**

Объект: проверенный snapshot `nipt_mngs_qc 1.10.0`, ранее выполненные PE126/SE50 проверки и серверная интеграция MetaX 2.0.3. Отчёт описывает существующий код, а не желаемую будущую архитектуру.

## 1. Главный вывод и границы готовности

**Pipeline технически проходит полный путь от FASTQ до профилей, сравнения фракций, QC JSON и MultiQC. Однако улучшение итогового QC после перехода на MetaX не означает улучшения удаления человеческих чтений.**

В завершённом серверном тесте MetaX:

- PE126: 17 из 17 задач завершились с `exit 0`; итог `PASS_POSITIVE`.
- SE50: также 17 из 17 задач с `exit 0`; итог `PASS_POSITIVE`.
- Для каждого образца получены четыре согласованных профиля: `dehost/full`, `dehost/patho`, `host/full`, `host/patho`. Все восемь штатных QC критериев прошли в каждом режиме. Основание — предоставленный серверный сборник `metax_review_minimal.txt`, содержащий 58 секций, включая 28 JSON. [1]

При этом в серверном SE `dehost.bam` пользователь уже независимо подтвердил **516 человеческих и 3 000 микробных чтений**, всего 3 516. Истинная человеческая доля в этом toy-наборе — **14,6758%**. MetaX сообщил human count 36, поэтому QC использовал **36 / 3 516 = 1,0239%** и пропустил критерий `<=5%`. Это не противоречие в арифметике: **истинное происхождение чтения и результат аннотатора — разные измерения**.

Дополнительный локальный проход HISAT2 `--sensitive` действительно уменьшил human-остаток до 61 чтения, но одновременно удалил одно дрожжевое чтение. Получилось 61 human + 2 999 microbial = 3 060, human 1,9935%. Заранее заданный критерий требовал и human `<=5%`, и сохранения всех 1 000 чтений каждого микроорганизма. **Критерий не выполнен; включать этот rescue по умолчанию нельзя.**

Поэтому переданы два строго разделённых инструмента:

1. `run_metax_confirm_v1.py` — повторный подтверждающий запуск уже существующего основного workflow на прежних входах и БД, с защитой исходников и происхождения результатов.
2. `se_dehost_rescue_v1.py` — неизменённый отдельный эксперимент, который пользователь может запустить после основного прогона. Он не исправляет core pipeline и не объявлен принятой оптимизацией.

**Статус «финальный» относится к исследовательскому описанию проверенного snapshot, а не к клинически валидированному тесту.** Новый серверный прогон `metax_confirm_v2` на момент подготовки отчёта ещё не выполнен. Хеш нового пользовательского Git-коммита после `git add .`/push не получен; утверждать, что именно этот pushed commit проверен, нельзя. Новый runner проверит runtime-содержимое по SHA256 и запишет Git commit/status.

## 2. Термины: что именно здесь измеряется

### 2.1. Предмет исследования

**cfDNA**, cell-free DNA, — внеклеточная ДНК. В данном проекте исследуется возможность метагеномного дополнения к данным НИПТ: анализировать не только человеческие последовательности, но и небольшой оставшийся нечеловеческий сигнал. Исследования плазменной cfDNA рассматривают такой подход к характеристике микробного сигнала, но это само по себе не превращает любой найденный таксон в диагноз. [2]

**НИПТ/NIPT** здесь задаёт контекст исходных данных. Этот pipeline не вычисляет фетальную фракцию, анеуплоидии или акушерский риск.

**mNGS**, metagenomic next-generation sequencing, — секвенирование смеси генетического материала без ограничения одним заранее выбранным микробным геномом. В данной реализации анализ ограничен содержимым конкретных референсных БД; отсутствующий в БД организм не становится наблюдаемым только благодаря слову «метагеномика».

### 2.2. Read, mate, pair и fragment

| Термин | Понятное определение | Единица в нашем примере |
|---|---|---|
| Read / прочтение | Одна прочитанная последовательность нуклеотидов | Одна FASTQ-запись |
| Mate | Один конец парного чтения | R1 или R2 |
| Pair | Два связанных mate одного фрагмента | Одна запись в R1 + соответствующая запись в R2 |
| Fragment / фрагмент | Единица происхождения последовательности; в PE обычно пара, в SE одно чтение | Счётчик профиля: PE — пары; SE — отдельные reads |
| PE126 | Paired-end: два конца с исходной длиной 126 nt | 600 000 пар = 1 200 000 read records |
| SE50 | Single-end: одно чтение исходной длиной 50 nt | 600 000 read records |

Важнейшее практическое правило: **6 008 BAM-записей PE DEHOST — это 3 004 пары, а не 6 008 пар**. Напротив, 3 516 SE BAM-записей — 3 516 единиц профилирования. После trimming длина PE-чтений может отличаться от исходных 126 nt.

### 2.3. Форматы

| Формат | Что хранит | Чего нельзя из него автоматически заключать |
|---|---|---|
| FASTQ | Идентификатор, последовательность, разделитель, качества оснований | Таксон не известен из обычного имени реального read |
| FASTA | Заголовок и последовательность | Нет исходной строки QUAL, координат, CIGAR |
| SAM | Текстовое описание выравнивания: QNAME, flags, reference, POS, MAPQ, CIGAR, SEQ, QUAL и tags | Одна строка не всегда равна одному уникальному исходному read |
| BAM | Бинарная форма данных SAM | Наличие BAM не означает, что все записи mapped или что BAM отсортирован по координатам |
| TSV / CSV | Таблицы, разделённые табуляцией / запятой | Расширение не гарантирует корректность разделителя |
| JSON | Именованные поля, числа, массивы, `null` | Валидный JSON не доказывает правильность биологического вывода |

SAM/BAM может содержать primary, secondary и supplementary записи одного read. Поэтому для подсчёта исходных наблюдений код исключает `0x100` и `0x800`, а не использует произвольное число строк BAM. Значения и назначение полей заданы спецификацией SAM. [3]

### 2.4. Качество оснований и качество картирования

Для качества основания используется шкала Phred:

`Q = −10 × log10(p_error)`.

Q30 соответствует номинальной вероятности ошибки основания 0,001. **Q30 rate** — доля оснований с Q не ниже 30; это не доля reads, которые «полностью правильные». Среднее Q тоже не равно Q30 rate. `QUAL` относится к основаниям; **MAPQ** — к неопределённости положения выравнивания, а не к правильности таксономической аннотации. [3]

Пример из завершённого rescue: дрожжевое чтение выровнялось на человеческий toy-reference с MAPQ 60. Это не сделало его человеческим по происхождению. У него было `19S31M`: только 31 основание участвовало в выравнивании, а 19 осталось soft-clipped.

### 2.5. Mapping, classification и abundance

- **Mapping / картирование**: поиск соответствия read выбранному reference. Здесь HISAT2 решает задачу относительно human index.
- **Unmapped**: подходящего выравнивания не найдено при данном reference, алгоритме и параметрах. Это **не синоним microbial**.
- **Taxid**: идентификатор узла таксономии; **rank** — его ранг, например species.
- **Classification / аннотация**: алгоритмическое отнесение сигнала к таксону.
- **Abundance estimate**: оценка количества или относительного вклада; может получаться перераспределением неоднозначных наблюдений, а не прямым подсчётом уникальных правильно размеченных reads.
- **Ground truth, GT**: известное происхождение искусственно сгенерированных reads. В этом toy GT восстанавливается из исходного идентификатора. У обычного клинического образца такой разметки нет.
- **QC verdict**: решение конкретных программных правил по доступным метрикам. Это не диагноз и не независимая оценка истинности аннотации.

## 3. Из чего состоит pipeline и какие версии относятся к какому запуску

### 3.1. Оркестрация

`main.nf` связывает процессы Nextflow DSL2. Модули в `modules/local/` выполняют конкретные задачи. Скрипты `bin/` реализуют подсчёты, конверсию форматов, сравнение профилей и QC.

Основной FASTQ-путь:

**samplesheet → fastp → HISAT2 → HOST / DEHOST / HALF → BAM2FASTA → аннотатор → profile.v2 → validator → сравнение → QC gate → MultiQC.**

Опциональная ветка `ALL` описана отдельно: её нельзя смешивать с вычисляемым `all` внутри comparison.

### 3.2. Пины кода и фактически наблюдавшиеся версии

| Компонент | Что зафиксировано / проверено |
|---|---|
| Pipeline | `manifest.version = '1.10.0'`; одного этого текста недостаточно для идентичности кода |
| HISAT2 | 2.2.3 в завершённой локальной проверке и отдельном rescue |
| fastp | 1.3.7 в проверенной среде |
| samtools | 1.24 в сохранённой локальной baseline-среде |
| Kraken2 | 2.17.2 в сохранённой локальной baseline-среде |
| Bracken | В директиве модуля указан 3.1; сохранённый локальный фактический вывод — `Bracken v3.0.1` |
| MetaX | 2.0.3, подтверждён серверным сборником |
| MultiQC | 1.35 в проверенной среде |
| Nextflow | Локальный baseline: 26.10.4; пользовательский сервер: 26.10.5 |
| Серверный основной Python / Java | По ранее полученным сведениям: Python 3.14.7 / Java 21 |

**Пин в директиве `conda` — не доказательство реально использованной версии при `-profile standard`.** В standard инструменты берутся из PATH. Поэтому новый runner сверяет реальные version outputs с сохранёнными серверными `logs/version_*.log`, а не приписывает серверу локальные версии из таблицы. Различие Bracken нельзя скрывать за общим номером pipeline. В новом MetaX-прогоне Bracken не вызывается.

### 3.3. Профили окружения

| Профиль | Поведение |
|---|---|
| `standard` | Инструменты уже установлены в основной среде и доступны через PATH |
| `conda` | Nextflow использует per-process `conda`-директивы |
| `docker` | Используются container-директивы; общий образ должен быть подготовлен |
| `test` | Отдельный небольшой smoke-набор и собственные облегчённые параметры; это НЕ `tests/insilico/toy/toy.config` |

Выполненный серверный MetaX-тест использовал **standard**, основное окружение `nipt_mngs_qc` и отдельный бинарник MetaX. **Общий Docker-образ нельзя считать автоматически содержащим MetaX**: комментарий/директива в модуле не устанавливает его в уже собранный образ.

Повторный runner добавляет на PATH каталог только с symlink `metax`. Он не активирует MetaX conda environment и не подменяет основной Python.

## 4. Входы: что нужно предоставить до вычислений

### 4.1. Режим FASTQ

Обязательные CSV-колонки: `sample,fastq_1,fastq_2`. Дополнительная: `single_end`.

Ниже **эквивалентная относительная запись схемы** для понимания. Runner не переписывает существующие серверные samplesheets:

```csv
sample,fastq_1,fastq_2,single_end
SAMOVAR_PE,reads/toy_PE_R1.fastq,reads/toy_PE_R2.fastq,false
```

```csv
sample,fastq_1,fastq_2,single_end
SAMOVAR_SE,reads/toy_SE50.fastq,,true
```

Правила `main.nf`:

- `sample` не должен быть пустым; повторные ID запрещены.
- Если `single_end` отсутствует, пуст или false — ожидается PE и второй FASTQ.
- При `single_end=true` второй FASTQ должен быть пуст.
- Относительный путь разрешается **от каталога самого CSV**, не от текущего shell-каталога. Этим занимается `resolveCsvPath`.
- Абсолютный путь или URI используется как задан; доступность проверяется.
- Для FASTQ-режима нужен `--host_index`, то есть префикс существующего HISAT2 index, а не имя human FASTA и не отдельный `.ht2` файл.

### 4.2. Режим BAM

Схема: `sample,dehost_bam,host_bam`.

В этом режиме считается, что upstream уже подготовил две фракции. Pipeline:

- **не запускает заново fastp и HISAT2**;
- не проверяет заново биологическую корректность upstream dehosting;
- считает primary records, получает FASTA и профили;
- использует `assets/no_fastp.json`;
- не имеет исходного fastp QC для оценки `q30_rate`, `trim_survival`, `consistency`: эти критерии получают NA;
- не получает HALF-фракцию из указанной двухколоночной схемы.

Отсюда важное ограничение: одинаковый итоговый статус FASTQ- и BAM-режимов не означает одинаковый объём выполненных проверок.

### 4.3. Таблица БД

Обязательные поля `dbsheet`:

| Поле | Смысл | Серверный MetaX-пример |
|---|---|---|
| `db_id` | Идентичность конкретной БД | `samovar_metax_full`, `samovar_metax_patho` |
| `annotator` | Выбор адаптера | `metax` |
| `path` | Путь к каталогу индекса | Существующие `db_full/`, `db_patho/` |
| `role` | Роль для downstream-логики | `full`, `patho` |

Профили должны быть сопоставимы по `sample_id`, роли, `db_id`, аннотатору и версии. Роли не подменяются сходством имён каталогов.

В доступной реализации есть адаптеры Kraken2+Bracken, MetaX и stub. **Stub предназначен для программных fixtures и не является биологическим анализом.**

### 4.4. Что означает full и patho именно в этом тесте

- `full`: toy-human + три микробных reference.
- `patho`: только три микробных reference.
- Панель мишеней: `562`, `4932`, `10847`.

`patho` — техническая роль БД. Включение таксона в эту БД/панель не доказывает его патогенность для пациента. В MetaX для этой роли дополнительно передаётся `--host 9606`, но пользовательская таблица pathogen–host–disease в проверенном запуске не передавалась. Native host/disease аннотации не дают основания превращать эту toy-панель в клинически курированную. [1, 4]

### 4.5. Что проверяется до начала

`main.nf` проверяет режим, обязательные параметры, таблицы и поддерживаемые фракции. Для аннотации обязательны `dehost` и `host`; `all` опционален.

Новый runner дополнительно проверяет:

1. 33 SHA256 для runtime, assets, MultiQC config, toy config/panel/taxonomy.
2. Точный набор `.nf` модулей/subworkflow и обычных файлов `bin/`: новый непроверенный runtime-файл не принимается молча.
3. Канонические JSON fingerprints ранее проверенных `prepare.json` и `build_metax.json`.
4. Все входные/подготовленные файлы и DB-файлы, привязанные этими manifests.
5. Бинарник MetaX, восемь частей human index, полный non-fractional MetaX index и taxonomy.
6. Реальные версии инструментов и отсутствие подмены основного Python.

Двадцать девять source/config fingerprints уже присутствовали в серверном prepare; четыре дополнительных пина относятся к assets и `multiqc_config.yaml`. Добавление `tools/validation/`, теста и документации не меняет проверяемый runtime-набор.

SHA256 подтверждает неизменность байтов относительно указанного основания, **но не качество reference, чувствительность метода или отсутствие биологических ошибок**.

## 5. Конкретный пример: что было сгенерировано

### 5.1. Источник и состав

Использован Samovar на зафиксированном ранее snapshot. В генерации задан seed 42. Сам Samovar различает число пар и число individual reads, передаваемых генератору; смешивать эти единицы нельзя. Реализация преобразования содержит `_iss_reads_for_pairs(n_pairs) = 2 × n_pairs`. [5, 6]

| Истинный источник | Source taxid | Видовой taxid в профиле | Исходных PE-пар | Производных SE50 reads |
|---|---:|---:|---:|---:|
| Human | 9606 | 9606 | 597 000 | 597 000 |
| Escherichia coli | 562 | 562 | 1 000 | 1 000 |
| Saccharomyces cerevisiae | 4932 | 4932 | 1 000 | 1 000 |
| phiX174 | 2886930 | 10847 | 1 000 | 1 000 |
| **Всего** | | | **600 000** | **600 000** |

На старте human = 99,5%, microbial = 0,5% по фрагментам. SE50 получен из **первых 50 оснований и соответствующих качеств R1** тех же PE-reads, а не независимой симуляцией. Поэтому сравнение PE126/SE50 одновременно меняет длину и pairedness. Оно не изолирует эффект только длины или только парности.

Входные mate-файлы были синхронно перемешаны с проверкой pairing. GT taxid находится в исходных идентификаторах и используется для независимой проверки, **не как подсказка HISAT2, Kraken2 или MetaX**.

### 5.2. Reference здесь намеренно маленький

| Reference | Длина, nt | Существенное ограничение |
|---|---:|---|
| Human | 3 413 920 | Toy-фрагмент, не полный human genome |
| E. coli | 3 999 920 | Использованный toy-reference, не универсальная панель штаммов |
| S. cerevisiae | 3 999 230, 7 contigs | Набор contigs конкретного toy |
| phiX174 | 5 386 | Очень короткий reference |
| **Всего full** | **11 418 456** | Маленькая закрытая смесь |

Серверный `reference_manifest.json` хранит соответствие source FASTA, исходных contig headers, новых MetaX headers и sequence hashes. Подготовка MetaX меняла заголовки, а не нуклеотиды. Human index ранее был независимо восстановлен через `hisat2-inspect` и сопоставлен с human FASTA. Подтверждения подготовки и длины находятся в серверных manifests. [1]

Таксономия содержит 43 реальных узла. Source phiX taxid 2886930 — узел `no rank` под видовым 10847, а не искусственно объявленный species. В профилях используется имя `Sinsheimervirus phiX174` и species taxid 10847. Сведение source к species — таксономическая нормализация, не фильтрация reads по GT. [7, 8]

### 5.3. Где расположен генератор и evaluator

`tests/insilico/toy/toy.py`:

- `generate`: запуск Samovar, получение исходных reads, shuffle и производный SE50;
- `inspect_fastq`, `check_pairs`: проверка состава/длины и pairing;
- `build`: подготовка исходных toy БД и human index;
- `pipeline`: запуск pipeline;
- `bam_truth`: оценка сохранённых BAM по GT;
- `acceptance`: заранее заданные проверки.

**В этой задаче эти стадии не запускались повторно.** Старый `acceptance.tsv` фактически записан как CSV из-за старого writer; его нужно читать с запятой. Этот дефект названия не исправлялся незаметно.

## 6. Стадия 1 — fastp: очистка FASTQ и исходное качество

| Аспект | Фактическое поведение |
|---|---|
| Вход | Исходные FASTQ: PE R1/R2 либо SE R1; с QUAL |
| Код | `modules/local/fastp.nf`, процесс `FASTP` |
| Явные настройки | `--length_required 35`, число потоков из `task.cpus`, JSON/HTML имена |
| Остальная обработка | Defaults установленного fastp; нельзя приписывать включение всех доступных функций |
| Выход downstream | `trim_R1.fastq.gz`; для PE также `trim_R2.fastq.gz` |
| Компактные результаты | `<sample>/qc/fastp/<sample>.fastp.json` и `.html` |
| Опциональная публикация reads | `<sample>/validation/trimmed/trim_R*.fastq.gz` |

fastp умеет оценивать качество, фильтровать reads, обрезать адаптеры и выполнять другие преобразования. Наличие такой функции в инструменте не значит, что pipeline явно включил её. В частности, здесь нельзя автоматически заявлять UMI-обработку, deduplication или принудительную одинаковую конечную длину всех reads. [9]

### 6.1. Что реально изменилось

| Величина | PE126 | SE50 |
|---|---:|---:|
| До: read records | 1 200 000 | 600 000 |
| После: read records | 1 174 786 | 592 216 |
| После: единицы профилирования при целых PE-парах | 587 393 пары | 592 216 reads |
| Потеря read records | 25 214 | 7 784 |
| Survival, точный расчёт | 97,8988% | 98,7027% |
| Raw Q30 rate в QC, округлённо | 90,69% | 95,30% |

PE microbial mates: исходно 6 000; после fastp 5 968, то есть 99,4667% сохранения. SE microbial reads: 3 000 → 3 000. Это результаты GT-проверки данного toy, не универсальная потеря microbial DNA от fastp.

Код QC использует:

- `q30_rate` **до** filtering: `summary.before_filtering.q30_rate`;
- `trim_survival = after_filtering.total_reads / before_filtering.total_reads`.

Это доля read records. Для нормальных синхронных PE-файлов она численно совпадает с долей сохранившихся пар, но формула читает именно `total_reads`. В BAM-режиме обе величины не восстанавливаются из выдуманного fastp-отчёта: они NA.

## 7. Стадия 2 — HISAT2 и точная партиция HOST / DEHOST / HALF

### 7.1. Что решает HISAT2

| Аспект | Реализация |
|---|---|
| Вход | Trimmed FASTQ с качествами + префикс human index |
| Код | `modules/local/dehost.nf`, затем **`bin/dehost_split.sh`** |
| Основной вызов | HISAT2 с `--no-spliced-alignment`; PE `-1/-2`, SE `-U` |
| Дополнительный `--sensitive` | **Не включён** в основной pipeline |
| Промежуточный формат | SAM → BAM через samtools |
| Критерий разбиения | SAM flags, не taxid и не MAPQ |
| Сохранённая сводка | `<sample>/qc/dehost/<sample>.hisat2.summary.txt` |
| Опционально | Три BAM в `<sample>/validation/partitions/` |

Выбор `--no-spliced-alignment` отключает поиск сплайсированных выравниваний. Это не означает запрет soft-clipping. HISAT2 по умолчанию может soft-clip концы; минимальный score задаётся функцией от длины. В руководстве default `--score-min L,0,-0.2`: для 50 nt это −10. Штрафы зависят в том числе от качества оснований. [10]

**Нет выравнивания** означает лишь, что выбранный алгоритм не сообщил приемлемое выравнивание на данный human reference при данных настройках. Причины могут включать ошибки reads, короткие/сложные последовательности, неполный reference и ограничения поиска; точная причина оставшихся reads требует отдельного исследования.

### 7.2. Разбиение по flags

Сначала исключаются secondary/supplementary: `-F 0x900`.

| Фракция | PE | SE | Биологическая интерпретация |
|---|---|---|---|
| HOST | Оба mate mapped на human reference | Read mapped | «Сработало human mapping», не гарантированное human-происхождение |
| DEHOST | Оба mate unmapped | Read unmapped | Кандидатная non-host фракция, но может содержать human |
| HALF | Ровно один mate mapped; сохраняются записи обоих концов | Пустая фракция | Неопределённая PE-группа, не удаляемая из учёта |

Здесь не требуется flag `proper_pair` и не применяется порог MAPQ. В частности, HOST — не только «идеально согласованные пары».

Настоящий фрагмент кода, иллюстрирующий SE/PE DEHOST:

```bash
samtools view -@ "$threads" -b -F 0x900 \
    -e '(flag.paired && flag.unmap && flag.munmap) || (!flag.paired && flag.unmap)' \
    -o "${out_prefix}.dehost.bam" "$in_bam"
```

Это алгоритмическое правило по flags. В нём нет проверки, что read имеет microbial GT.

### 7.3. Реальные размеры фракций

| Фракция | PE primary BAM records | PE pairs | SE primary records / reads |
|---|---:|---:|---:|
| HOST | 1 167 868 | 583 934 | 588 700 |
| DEHOST | 6 008 | 3 004 | 3 516 |
| HALF | 910 | 455 | 0 |
| **Всего** | **1 174 786** | **587 393** | **592 216** |

Суммы равны fastp after:

- PE: `1 167 868 + 6 008 + 910 = 1 174 786`.
- SE: `588 700 + 3 516 + 0 = 592 216`.

Следовательно, в проверенном примере primary records не исчезли между trimming и этими тремя фракциями. Это **проверка сохранения количества**, а не доказательство правильного назначения каждой записи. Эти upstream counts одинаковы в сопоставленных Kraken/MetaX результатах. [1]

### 7.4. Что показал независимый GT

| Истинное содержимое DEHOST | PE mates | PE pairs | SE reads |
|---|---:|---:|---:|
| Human | 40 | 20 | 516 |
| E. coli | 1 992 | 996 | 1 000 |
| Yeast | 1 986 | 993 | 1 000 |
| phiX | 1 990 | 995 | 1 000 |
| **Всего** | **6 008** | **3 004** | **3 516** |

В обоих режимах **все пережившие fastp microbial reads оказались в DEHOST**. Это не утверждение о сохранении всех исходных PE microbial reads: до этой стадии fastp уже потерял 32 mates.

Истинная human contamination DEHOST:

- PE: `40 / 6 008 = 20 / 3 004 = 0,6658%`.
- SE: `516 / 3 516 = 14,6758%`.

Из PE баланса также следует, что 910 HALF mates в этом примере human: весь сохранённый microbial GT уже находится в DEHOST. Это вывод для данного toy, а не свойство HALF в общем случае.

## 8. Стадия 3 — BAM2FASTA и подсчёт единиц

| Аспект | Реализация |
|---|---|
| Вход | Каждая из BAM-фракций |
| Модуль | `modules/local/bam2fasta.nf`, процесс `BAM2FASTA` |
| Подготовка | `samtools collate` перед извлечением FASTA |
| Исключение дубликатов выравнивания | `-F 0x900`, то есть secondary/supplementary, а не PCR duplicate flag |
| PE-выход | `<fraction>_1.fasta`, `<fraction>_2.fasta`, например `dehost_1.fasta` |
| Непарный выход | `<fraction>_0.fasta`, `<fraction>_s.fasta`; объединяются в `<fraction>_se.fasta` |
| Счётчики | `bin/bam_counts.py`: `view_count`, `count_bam` |
| Публикуется | `<sample>/qc/counts/*.counts.json`, `<sample>/qc/flagstat/*.flagstat.txt` |
| Обычно остаётся в work | FASTA-последовательности |

`collate` собирает записи одинакового имени рядом, чтобы mates корректно попали в парные файлы. Это не координатная сортировка и не удаление биологических дубликатов. `samtools fasta` разделяет READ1/READ2, category-0 и singletons; для парной выгрузки важна группировка по имени. Soft-clipped последовательность остаётся частью выгруженного read, если не применён специальный режим её удаления. [11]

### 8.1. Что теряется

После перехода FASTQ/BAM → **FASTA** остаются последовательности и заголовки. Входные per-base quality values дальше не передаются. Следовательно:

- fastp и первоначальный HISAT2 видели качества;
- аннотаторы в текущем workflow получают FASTA, а не исходный FASTQ;
- нельзя объяснять результат MetaX как непосредственное использование прежней QUAL-строки этим вызовом.

### 8.2. Как считается fragments

`bam_counts.py`:

Строка в возвращаемом словаре `count_bam`:

```python
"fragments": paired // 2 + unpaired,
```

`primary_reads` — число записей без `0x900`; `paired_reads` — среди них с flag PAIRED; остальные — `unpaired_reads`. `single_end` выставляется по отсутствию paired records.

Для нормальных целых пар это даёт правильное число фрагментов. Но скрипт не проводит полную валидацию любого произвольного смешанного BAM с одиночными mates. Возможны проблемы при странных flags, повторных QNAME или неполных парах; `primary_reads` не доказывает уникальность исходных молекул.

У пустой фракции `paired_reads=0`, поэтому локально она определяется как single-end даже внутри PE-образца. Это особенность счётчика, не превращение всего образца в SE. В нашем PE HALF не пуст, а в SE HALF пуст.

### 8.3. Размеры FASTA в проверенном примере

| Фракция | PE R1 records | PE R2 records | SE records |
|---|---:|---:|---:|
| HOST | 583 934 | 583 934 | 588 700 |
| DEHOST | 3 004 | 3 004 | 3 516 |
| HALF | 455 | 455 | 0 |

HOST и DEHOST поступают в аннотацию; **HALF отдельно не профилируется** в проверенной конфигурации, но его counts участвуют в consistency.

## 9. Опциональный ALL: два разных значения одного слова

**Эта деталь принципиальна: в коде существуют два неэквивалентных ALL.**

### 9.1. Реальная объединённая последовательность

Если включить `params.fractions = 'dehost,host,all'`, `modules/local/make_all.nf`:

- в FASTQ-ветке объединяет FASTA **DEHOST + HOST + HALF**;
- в BAM-ветке — **DEHOST + HOST**, потому что входной схемой HALF не передаётся;
- суммирует counts через `bin/sum_counts.py`;
- может отдельно аннотировать объединённый FASTA.

Для FASTQ toy число реальных ALL units составило бы 587 393 PE-пары или 592 216 SE-reads. Это арифметика размера входа, **не результат нового реально выполненного профилирования ALL**. В подтверждённом MetaX-запуске было четыре профиля на образец, то есть без дополнительной ALL-аннотации.

### 9.2. Синтетический all в comparison

При паре сравнения `dehost:all` функция `bin/compare_profiles.py:synthesize_all` складывает **уже рассчитанные профили DEHOST + HOST**, включая их знаменатели. Она:

- не читает отдельно аннотированный реальный ALL;
- не включает HALF даже в FASTQ-режиме;
- не повторяет совместное профилирование смеси.

Для PE его знаменатель — `3 004 + 583 934 = 586 938`, а не 587 393. Для SE HALF=0, поэтому различие размера исчезает, но алгоритмически это всё равно сумма отдельных оценок. В частности, EM-оценка на объединённом входе не обязана совпадать с суммой двух отдельных EM-оценок.

**В рамках этой задачи такое поведение описано, но не изменено.** Нельзя использовать эти два ALL как взаимозаменяемые методы или независимую проверку.

## 10. Стадия 4 — таксономическое профилирование

### 10.1. Kraken2 + Bracken

| Аспект | Фактическая реализация |
|---|---|
| Модуль | `modules/local/annotate_kraken2_bracken.nf` |
| Вход | FASTA HOST/DEHOST и БД из dbsheet |
| Kraken2 | `--confidence 0.15`; PE `--paired`; SE без `--paired` |
| Сохранение raw read assignments | **Нет**: `--output /dev/null` |
| Сохранённый native | `<sample>/qc/kraken/<sample>.<fraction>.<role>.kraken2.report` |
| Bracken | Видовой уровень `-l S`, порог `-t 10`, `-r 126` либо `-r 50` для этого benchmark |
| Конвертер | `bin/kraken2_bracken_to_profile.py` |
| Публикуется downstream | `profile.tsv`, `profile.json` |

Kraken2 использует minimizers k-mers и их таксономические LCA в compact hash table. Нельзя буквально описывать Kraken2 как хранение всех полных k-mers в том же виде, что Kraken1. Его `confidence` — доля поддерживающих k-mers относительно пригодных для запроса, **не калиброванная вероятность правильного таксона**. PE учитывается как одно sequence-pair событие в отчёте. [12]

Для длины 50 nt при k=35 всего 16 перекрывающихся k-mer позиций до учёта N/других особенностей; для 126 nt — 92. Это поясняющая арифметика, а не измерение числа независимых доказательств: перекрывающиеся k-mers зависимы, и Kraken2 запрашивает minimizers.

Bracken использует Kraken reports и вероятностную информацию о БД для переоценки abundance на выбранном ранге, в том числе перераспределяя более высокоуровневые назначения. Поэтому `new_est_reads` — оценка, а не таблица истинных индивидуальных read labels. Требуется подходящая read-length статистика БД. [13]

В модуле сначала проверяется наличие species-строки Kraken с clade count не ниже порога Bracken. Если подходящих строк нет, вместо падения Bracken создаётся пустая таблица с заголовком. Это допустимый пустой результат, который дальше оценивает QC.

**Важно про файлы:** native Bracken TSV создаётся в work как промежуточный файл, но не объявлен самостоятельным публикуемым output этого процесса. Не следует обещать его постоянное наличие в компактном results tree после очистки work.

### 10.2. Что берёт Kraken-конвертер

`parse_kraken_report`:

- `input_reads = U + R`, то есть unclassified + root clade;
- `classified_reads = R`;
- `unclassified_reads = U`.

`parse_bracken_taxa`:

- видовые строки;
- `reads = new_est_reads`;
- `abundance = reads / input_reads`, **не** нативный `fraction_total_reads` Bracken.

Из-за отсутствия raw Kraken per-read output нельзя восстановить точную confusion matrix аннотатора из этих сводок.

### 10.3. MetaX 2.0.3

| Аспект | Фактическая реализация |
|---|---|
| Модуль | `modules/local/annotate_metax.nf` |
| Подготовка | `bin/metax_prepare.py` |
| Запуск | `metax profile -d DB --dmp-dir DB/taxonomy -i ... -o metax_run -t task.cpus --no-progress` |
| PE | Дополнительно `-I mate2` |
| patho | Дополнительно `--host 9606` |
| Пустой вход | Не запускает падающий на пустом файле profiler; создаёт пустой native и валидный empty profile |
| Конвертер | `bin/metax_to_profile.py` |
| Native output | `<sample>.<fraction>.<role>.metax.txt` в profiles |
| Не сохраняется этим вызовом | Per-read `.classify.txt`, raw pre-filter profile, coordinate mappings |

MetaX использует встроенный mapper, таксономические/координатные свидетельства и EM-перераспределение неоднозначного abundance. Mapping, решение о присутствии таксона и итоговый count — разные уровни алгоритма. Нативный профиль уже прошёл собственные фильтры MetaX; отсутствующая строка не обязательно означает отсутствие любых кандидатов выравнивания. [14]

Для SE функция `unique_fasta_ids` заменяет заголовки на `metax_se_1`, `metax_se_2`, …, сохраняя порядок и последовательности. Причина — предотвращение слияния независимых records по одинаковому QNAME. PE-подготовка такого переименования не делает. Это техническое изменение идентификатора, не удаление human reads и не GT-фильтр.

Требуемый каталог:

```text
db_full/ или db_patho/
  metax_db.mxi
  metax_db.tsv.gz
  taxonomy/
    nodes.dmp
    names.dmp
    merged.dmp
    delnodes.dmp
```

Требуется `#fractional false`. Fractional MetaX индекс масштабирует поддержку по отношению полной и индексированной длины; такой режим нарушил бы используемый здесь count contract. Поэтому адаптер и runner его отклоняют. Пустые `merged.dmp`/`delnodes.dmp` допустимы: «пустой файл» не всегда означает испорченную БД. [14]

### 10.4. Нативные колонки MetaX и основная ловушка abundance

Native community profile содержит 13 колонок без заголовка:

1. name;
2. taxid;
3. rank;
4. reads;
5. depth;
6. abundance (%);
7–9. observed/expected breadth и связанная p-value;
10–13. chunk breadth показатели и p-value.

При `--host` добавляются ещё три: host names, host taxids, diseases. Именно 13/16 колонок проверены в серверных результатах. Нативные p-values — внутренние модельные характеристики coverage, не p-value клинической инфекции. [1, 14]

В просмотренном исходнике MetaX `community.rs` abundance нормируется по EM depth среди сообщённых taxa. Поэтому это не доля reads. В нашем маленьком phiX reference одна и та же поддержка reads даёт гораздо большую глубину, чем в многомиллионном бактериальном/дрожжевом reference. В PE phiX имеет около трети микробных counts, но native `abundance` **99,72748%**; в SE — **99,72634%**. Это не означает, что 99,7% reads относятся к phiX. [1, 15]

Контракт адаптера намеренно хранит разные величины раздельно:

- `reads` — native count;
- `abundance = reads / input_reads` — доля от всей входной фракции;
- `x_abundance_pct` — нативный процент MetaX;
- дополнительные поля `x_*` — нативные метрики, не подмена основных полей.

## 11. Стадия 5 — единый profile.v2 и его валидация

### 11.1. Зачем нужен contract

QC и comparison не должны разбирать каждый native-формат заново. Адаптер приводит их к общей паре:

- `<sample>.<fraction>.<role>.profile.tsv`;
- `<sample>.<fraction>.<role>.profile.json`.

TSV хранит таксоны; JSON sidecar — идентичность образца, fraction, role, DB, annotator/version, счётчики и status.

Обязательные TSV-колонки:

`sample, fraction, annotator, annotator_version, db_id, taxid, name, rank, reads, abundance`.

Дополнительные поля допускаются с префиксом `x_`.

### 11.2. Особое значение classified в MetaX-адаптере

`bin/metax_to_profile.py`:

```python
classified = min(input_reads, int(math.ceil(total_reads))) \
    if status == "ok" else 0
unclassified = input_reads - classified
```

Здесь `total_reads` — сумма **сообщённых native counts**. Конвертер допускает малое расхождение из-за пяти десятичных знаков нативного вывода, но отклоняет очевидное превышение input и нечисловые/отрицательные counts.

Следовательно, в MetaX contract:

- `classified_reads` — целочисленная масса поддержки после отчётных фильтров;
- `unclassified_reads` — остаток до input;
- это **не обязательно** количество reads, у которых mapper вообще не нашёл кандидата.

У Kraken счётчики U/R взяты из другой стадии алгоритма. Общие имена полей обеспечивают совместимость программы, **не идентичность измерительной процедуры**. Сравнивать `classified_frac` между аннотаторами нужно с этим ограничением.

### 11.3. Что validator действительно гарантирует

Код: `modules/local/validate_profile.nf` → `bin/validate_profile.py` → `bin/profile_io.py`.

Ключевые функции:

- `load_sidecar`;
- `load_taxa`;
- `read_profile`;
- `try_read_profile`.

Проверяются обязательные ключи/колонки, счётчики и связь `input = classified + unclassified`, допустимый status, согласование TSV/JSON identity, диапазон abundance, непустые taxid/name/rank и допустимая сумма taxon counts относительно classified.

При этом нельзя приписывать валидатору то, чего он не делает:

- он не сравнивает GT и предсказание;
- не доказывает наличие таксона в реальном образце;
- не является полной проверкой любой возможной особенности произвольного TSV;
- не обеспечивает повсеместно проверку дубликатов taxid или равенства `abundance = reads/input` для любого стороннего адаптера;
- успешный contract не исключает статистических или таксономических ошибок.

Пустой профиль с заголовком и корректным sidecar — валидный `status=empty`, а не обязательно ошибка pipeline. Пример: HOST/patho в завершённом MetaX-тесте.

## 12. Стадия 6 — сравнение DEHOST с HOST

| Аспект | Реализация |
|---|---|
| Модуль / скрипт | `modules/local/compare.nf` / `bin/compare_profiles.py` |
| Вход | Уже проверенные profile.v2 для одного sample и role |
| Основная пара | `dehost:host` |
| Порог presence A | `reads_A >= 10` |
| Порог presence B | `reads_B >= 10` |
| Нормировка | RPM от input каждой фракции |
| Выход | `*.dehost_vs_host.compare.tsv` и `.json` в profiles |

### 12.1. RPM и fold

Для таксона t:

`RPM_A(t) = reads_A(t) / input_A × 1 000 000`.

`fold(t) = RPM_A(t) / RPM_B(t)`, если `RPM_B > 0`; иначе бесконечность.

Категории:

- `both` — достигнуты оба абсолютных порога;
- `only_A` — достигнут только порог DEHOST;
- `only_B` — достигнут только порог HOST;
- ниже обоих порогов — строка не рассматривается.

**Фактическое правило enriched строже обычного «fold≥10»:**

```python
enriched = (present_a and not present_b
            and (rpm_b == 0 or fold >= args.enrichment_fold))
```

Если таксон `both`, он **никогда** не enriched в этой реализации, даже при большом RPM fold. Это правило кода, а не универсальное определение биологического обогащения.

### 12.2. Реальный пример: E. coli в PE MetaX full

- DEHOST count: 991, input 3 004.
- HOST count: 0, input 583 934.
- `RPM_DEHOST = 991/3004×10^6 = 329 893,48`.
- `RPM_HOST = 0`.
- Категория `only_A`; enriched=true.
- В TSV fold записан `Inf`; в JSON бесконечный fold представлен `null`, а не невалидным JSON числом.

В том же full comparison human:

- DEHOST 20, HOST 580 489;
- оба count не ниже 10;
- категория `both`, enriched=false.

Числа и категории непосредственно присутствуют в серверном comparison. [1]

`only_A` означает «HOST ниже порога presence», не обязательно абсолютно нулевой биологический фон. Бесконечный fold при нуле в HOST не является измеренной бесконечной биологической величиной.

### 12.3. Сходство профилей

- Jaccard = число shared taxa / число taxa в union после presence-фильтра.
- Bray–Curtis dissimilarity = `Σ|RPM_A−RPM_B| / Σ(RPM_A+RPM_B)` на рассматриваемых строках.
- Spearman считается только на shared taxa; при менее двух shared или нулевой вариации возвращается `null`.

В MetaX full: shared=1, only_A=3, only_B=0, Jaccard=0,25 для PE и SE. Bray–Curtis: PE 0,993300; SE 0,988309. В patho: shared=0, only_A=3, Jaccard=0, Bray–Curtis=1. Spearman в этих случаях NA, а не «нулевая корреляция». [1]

Сходство/различие фракций не является независимым тестом инфекции. **HOST — внутренний алгоритмический компаратор, а не wet-lab negative control.** Он не заменяет extraction blanks, library blanks, положительные контроли и проверку batch contamination.

## 13. Стадия 7 — QC gate: формулы, пороги и итоговое решение

### 13.1. Обязательные артефакты

`modules/local/qc_gate.nf` вызывает `bin/qc_gate.py`.

Для штатного решения нужны:

- HOST/DEHOST counts JSON;
- четыре пары profile.tsv/profile.json;
- две comparison JSON для `dehost:host`, full/patho;
- настоящий fastp JSON для FASTQ-ветки либо корректный BAM stub.

Отсутствующие/битые обязательные артефакты фиксируются как `FAIL / PIPELINE_ERROR`, когда QC gate получил возможность выполниться. `main.nf` старается сохранить образцы в QC через authoritative sample list и missing stubs. Но если upstream-процесс завершился с fatal execution error и Nextflow остановился раньше, готовый QC report может отсутствовать: это нужно диагностировать по логам/trace, а не обещать JSON при любом краше.

HALF count в текущем Python QC опционален: отсутствующий или непарсящийся HALF может быть заменён на ноль. Поэтому нельзя утверждать, что любая порча HALF обязательно немедленно даёт hard FAIL. Для FASTQ ожидается реальный counts файл HALF; consistency способен выявить часть таких проблем.

### 13.2. Восемь штатных критериев

| Критерий | Формула / источник | Default | Этот Samovar toy | Нарушение |
|---|---|---:|---:|---|
| `input_pairs` | fragments_D + fragments_H | ≥5 000 000 | ≥100 000 | `FAIL / LOW_INPUT` |
| `host_fraction` | primary_H / (primary_H + primary_D) | ≥0,95 | ≥0,993 | `FALLBACK / HOST_FRACTION_LOW` |
| `nonhost_pairs` | fragments_D | ≥50 000 | ≥1 000 | `FALLBACK / ZERO_MICROBIOME` |
| `q30_rate` | fastp before_filtering Q30 base fraction | ≥0,80 | ≥0,80 | `FALLBACK / LOW_QUALITY` |
| `trim_survival` | fastp after reads / before reads | ≥0,90 | ≥0,90 | `FALLBACK / LOW_QUALITY` |
| `consistency` | `abs(H+D+HALF−trim_after)/trim_after` | ≤0,01 | ≤0,01 | `FALLBACK / SPLIT_INCONSISTENT` |
| `dehost_human_frac` | reported taxid9606 reads / full-DEHOST input | ≤0,05 | ≤0,05 | `FALLBACK / DEHOST_FAILURE` |
| `classified_frac` | full-DEHOST classified / input | ≥0,0001 | ≥0,0001 | `FALLBACK / NO_CLASSIFIED_SIGNAL` |

Defaults — имеющиеся параметры кода, **не доказанная клиническая калибровка**. Toy overrides — software acceptance settings, а не рекомендованные пороги для реальных образцов.

### 13.3. Три неочевидных знаменателя

1. **`input_pairs` — исторически неточное имя.** В SE это количество reads, а не пар. В обоих режимах HALF исключён. В PE здесь 586 938, а не raw 600 000 и не trimmed 587 393.
2. **`host_fraction` исключает HALF.** PE `1 167 868/(1 167 868+6 008)=0,994882`. Если включить HALF в знаменатель, получится другая доля. В штатном QC используется первая.
3. **Human contamination оценивается по full-профилю, а не непосредственно из HISAT2 flags или GT.** Если human строка не сообщена или БД не содержит human, числитель может быть нулём. Ноль не доказывает отсутствие human.

Human criterion не оценивается при недостаточном `nonhost_pairs`: тогда основная проблема — нехватка не-host сигнала. В BAM-режиме Q30/survival/consistency имеют `pass=null`, то есть NA, а не true.

`half_mapped_frac = HALF/(H+D+HALF)` — дополнительная информационная метрика; отдельного cutoff для неё здесь нет. Она влияет на вердикт через consistency, если сумма перестала совпадать.

Округлённые значения в JSON/TSV удобны для чтения, но сравнение с порогом в Python происходит на рассчитанной величине. Не стоит вручную переоценивать пограничный образец только по округлённой печати.

### 13.4. Позитивность панели

Панель принимает taxid либо имя по одной записи на строку; пустые строки и комментарии игнорируются.

Правило:

1. Взять `enriched_taxa` из **patho comparison**.
2. Пересечь с panel taxid/именами.
3. Посчитать hits.

Это не правило «любой найденный микроб делает образец положительным» и не правило «любой full-profile hit достаточно».

Если панель не передана, `positivity_source=not_evaluated`. При пройденном QC может получиться `PASS_NEGATIVE`, но его нельзя читать как доказанный клинически отрицательный результат: позитивность в таком случае не оценивалась.

### 13.5. Приоритеты статусов

```text
Есть hard FAIL → FAIL
Иначе есть soft failure → FALLBACK
Иначе есть panel hits → PASS_POSITIVE
Иначе → PASS_NEGATIVE
```

В QC JSON:

- `status` — итог;
- `fallback_reasons` — коды причин;
- `criteria` — значения, пороги, pass/NA, severity;
- `metrics` — количественные показатели;
- `target_panel` — файл, число targets, имена hits;
- `comparison_info` — сводка сравнений;
- `annotator`, `db_id`, `pipeline_version` — происхождение.

Jaccard/Bray–Curtis/Spearman информационные. Но **enriched patho taxa участвуют в позитивности**, поэтому неверно говорить, что comparison вообще никак не влияет на verdict.

### 13.6. Почему exit 0 и QC FAIL могут сосуществовать

`qc_gate.py` может корректно рассчитать и записать `FAIL` или `FALLBACK`, затем закончить работу с exit 0. Для Nextflow программа выполнилась успешно. Для образца QC не пройден.

Нужно различать четыре уровня:

| Уровень | Что проверяет | Чего не доказывает |
|---|---|---|
| Workflow execution | Команды/задачи завершились, outputs созданы | Приемлемость образца |
| QC | Выполнены заданные пороги по доступным метрикам | Истинные таксоны и отсутствие contamination |
| GT evaluation | Согласие с известной разметкой данного toy | Качество на неизвестных реальных образцах |
| Клиническая валидация | Требует отдельного дизайна и независимых данных | Не заменяется ни одним из предыдущих уровней |

## 16. Отдельный sensitive-rescue: что выполнено и почему не внедрено

### 16.1. Вход и воспроизводимость

Существующий `se_dehost_rescue_v1.py` работает отдельно от Nextflow. В локальном эксперименте проверены:

- исходные PE/SE FASTQ и human FASTA hashes;
- все восемь частей human index;
- совпадение реконструированных последовательностей index с human reference;
- 3 516 уникальных primary unmapped unpaired records по 50 nt;
- соответствие исходным SE50 bases и QUAL; 335 различий только регистра букв после BAM-нормализации не считались нуклеотидными заменами.

Локальные fingerprints:

| Объект | SHA256 |
|---|---|
| Локальный входной BAM | `9541001fe0b7484e41d825e588c4840c7a5b5248b32ed4ab1100a4c0e85c619c` |
| QNAME-set | `9ee583d3f760bf6cbe7c2ea08de25b4cdd4c52b1b0fc51d9a21072bebd067745` |
| Отсортированный QNAME/SEQ/QUAL content | `2207b018908adfc5cea7017c3249e9932f505c64963fd846533f67af5aa9b954` |

Хеш текущего серверного BAM не был предоставлен. Поэтому локальный эксперимент и серверный вход согласуются по известным данным, но **их побайтовая идентичность не установлена**.

### 16.2. Предзаданный дизайн

Ровно два режима HISAT2 2.2.3:

1. Control: `--no-spliced-alignment`, без нового preset.
2. Candidate: то же + `--sensitive`.

В каждом сначала pilot первых 256 records в существующем порядке, затем полный набор; два потока. Pilot — проверка исполнения/ресурсов, не случайная независимая validation set. При ненулевом mapping control кандидат не должен запускаться: replay исходного dehosting не воспроизведён.

В установленном CLI sensitive раскрывается в:

`--bowtie2-dp 1 -k 30 --score-min L,0,-0.5`.

То есть меняется не одна score threshold. Нельзя причинно приписать весь эффект исключительно ослаблению `score-min`.

Mapping-only partition определяет removed/retained по новому mapped flag. GT используется **после** этого для оценки, не для решения, какие reads сохранить.

### 16.3. Полные результаты

| Величина | До | После control | После sensitive |
|---|---:|---:|---:|
| Human retained | 516 | 516 | 61 |
| E. coli retained | 1 000 | 1 000 | 1 000 |
| Yeast retained | 1 000 | 1 000 | **999** |
| phiX retained | 1 000 | 1 000 | 1 000 |
| Всего retained | 3 516 | 3 516 | 3 060 |
| Human fraction | 14,6758% | 14,6758% | 1,9935% |

Удалено 455/516 = **88,1783%** human. Microbial retention 2 999/3 000 = **99,9667%**. Для заранее заданного требования «все 1 000 каждого микроба» последнее недостаточно.

Решение: **DO_NOT_DEPLOY**. Даже небольшая потеря не маскируется округлением до 100%. В этой задаче не проводился дополнительный подбор preset/threshold и не ослаблялся критерий приёмки после просмотра результата.

### 16.4. Одно потерянное чтение — конкретный пример

| Поле | Наблюдение |
|---|---|
| QNAME | `taxid:4932_478_0/1` |
| GT | Yeast, taxid4932 |
| Новый flag | 16, reverse mapped SE |
| Human contig | `Hsap.fna\|taxid:9606\|-NC_000001.11` |
| POS | 3 400 128, SAM 1-based |
| MAPQ | 60 |
| CIGAR | `19S31M` |
| AS | −19 |
| NM | 0 |

Интерпретация: 19 оснований soft-clipped, 31 входит в alignment; NM=0 относится к выровненной части и не означает 50/50 совпадающих оснований. Высокий MAPQ не защитил бы этот microbial read от human removal. Клиппинг допустим без отдельного запрета `--no-softclip`. [3, 10]

Среди 455 удалённых human: AS от −25 до −5; 162 ниже −10 и 293 не ниже −10; у 109 есть soft clipping. Это ещё одна причина не объяснять поведение только сменой минимального score.

Оставшиеся 61 human не были механистически разобраны до однозначной причины. ### 17.2. Что содержит новый review_minimal.txt

Collector автоматически добавляет:

- provenance, Git commit/status и точные argv;
- версии, resolved config;
- старые prepare/build/reference manifests, execution config, dbsheet;
- counts, contract/native profiles, comparisons;
- QC JSON и MultiQC custom TSV;
- fastp summary/filtering_result, без больших quality curves;
- traces и не более 120 последних строк соответствующих log/task stdout/stderr, с дополнительным байтовым пределом.

Нет FASTQ, FASTA, BAM, DB, MetaX cache, install log, полного work или environment dumps. Collector не собирает `.command.run`, где может находиться окружение процесса. Payload ограничен 2 MiB плюс небольшой receipt; отдельный файл — не более 128 KiB, при отсечении есть явная пометка. Поэтому это удобный файл для review, **не полный архив для восстановления анализа**.

В receipt записываются пути, размеры и SHA256 включённых/пропущенных кандидатов. Если секция обрезана, оригинал остаётся на сервере; для дополнительной проверки можно запросить именно его.

### 17.3. Work, published outputs и resume

Nextflow хранит промежуточные файлы задач в `work`, а cache metadata — в `.nextflow/cache` относительно launch directory. Для корректного resume нужны оба, а не только скопированный HTML или results tree. Наличие `-resume` не гарантирует переиспользования задач при изменении входов, скриптов или отсутствии необходимых task outputs. [17]

В новом runner:

- PE и SE имеют разные launch/work/log/results;
- два полных запуска идут последовательно;
- **нет неявного `-resume`**;
- existing outdir отклоняется, даже после неудачной попытки;
- прежние manifests/results не перезаписываются;
- нет удаления старых work/DB/reads;
- не устанавливаются инструменты и не пересобираются БД.

Не удаляйте work/cache и validation artifacts до завершения разбора расхождений. Отдельный Git-repository не должен становиться хранилищем всех runtime outputs; однако данный runner не чистит Git и не исправляет задним числом уже выполненный `git add .`.

### 19.2. Runner: fail-closed, а не автоматический «ремонт»

Runner не меняет pinned hashes при несовпадении. Он останавливается, сохраняет доступную диагностику и требует review конкретных изменений.

Существующие manifests содержат абсолютные серверные пути. Runner рассчитан на их **исходное местоположение** и не переписывает manifests ради переноса. «Переносимые тесты» означает отсутствие зависимости тестов от конкретного аккаунта/сервера; это не обещание, что подготовленную БД с абсолютным execution.config можно без подготовки перенести куда угодно.

Для защиты от постороннего `~/.nextflow/config` используется Nextflow `-C` с двумя конкретными файлами: прежним `nextflow.config` и прежним `metax_samovar_v1/execution.config`. Это изоляция конфигурации, а не новые параметры алгоритма. Синтаксис и precedence проверены командой `nextflow config`, без запуска workflow.

Сохранены:

- standard profile;
- 4 CPU / 8 GB для используемых процессов;
- resource ceiling 4 CPU / 8 GB / 24 h;
- local executor, `queueSize=1`;
- прежние toy thresholds и panel;
- `publish_validation_artifacts=true`;
- отдельные последовательные PE/SE запуски.

Ограничение ресурсов Nextflow не равно обещанию kernel-level RAM cgroup при local executor. HISAT2/samtools также могут иметь вспомогательные threads; `cpus=4` — настройка задачи, а не измеренный абсолютный предел числа OS threads.

## 21. Ограничения и разумное следующее исследование

### 21.1. Что данный toy не способен установить

1. **Clinical sensitivity/specificity, LOD, PPV/NPV.** Здесь один малый закрытый искусственный состав, не клиническая когорта.
2. **Поведение на всём human genome.** Human reference — 3,4 Mb toy-фрагмент.
3. **Устойчивость к штаммам вне БД.** Те же ограниченные references участвуют в построении теста и индексов.
4. **Разделение эффекта длины и pairedness.** SE50 производен от R1 PE126; два фактора изменены одновременно.
5. **Индивидуальную точность аннотации.** Нет сохранённых per-read assignments Kraken/MetaX в рассмотренном материале.
6. **Причину каждого human false negative.** Summaries не заменяют разбор alignment candidates и filters.
7. **Независимую репликацию.** Два аннотатора используют те же reads, а новый confirm-run воспроизводит тот же benchmark.
8. **Отличие инфекции от contamination/background.** HOST comparator не заменяет лабораторные контроли и клиническую информацию.

### 21.2. Что логично делать после нового review

Сначала — проверить воспроизводимость server confirm/rescue без изменения thresholds. Если расхождение есть, сравнить hashes, версии, input units и trace, а не сразу подбирать более удобные настройки.

Отдельным следующим исследованием можно:

- оценить host-removal непосредственно по GT и при нескольких уровнях human contamination;
- разделить длину и pairedness в факторном дизайне, добавить независимые seeds/составы;
- включить absent taxa, близкие виды/штаммы, сложные реальные references и лабораторные отрицательные контроли;
- в заранее согласованном ограниченном эксперименте сохранить read-level assignments/raw profiles для диагностики;
- разработать annotator-independent или независимо проверяемую оценку human leakage;
- рассматривать чувствительный дополнительный mapping только с заранее определённым допустимым microbial loss и отдельной validation set.

Это предложения, **не выполненные в этой задаче анализы**. Порог потерь не пересматривается задним числом ради принятия уже просмотренного sensitive-результата.

## 22. Итог в одной цепочке

Мы начали с 600 000 PE-пар, 99,5% human, и связанного SE50 набора. Fastp сократил количество records; HISAT2 разделил оставшиеся по human mapping flags. BAM2FASTA подготовил последовательности без исходных qualities. Аннотаторы оценили таксономический состав HOST/DEHOST, конвертеры привели его к profile.v2, comparison посчитал пороговое enrichment, QC применил восемь правил и панель, MultiQC показал уже рассчитанные метрики.

**Технически рабочая интеграция MetaX подтверждена. Биологическая проблема human leakage в SE остаётся: 516/3 516 по GT, несмотря на QC PASS. Sensitive-rescue уменьшает human, но не проходит условие сохранности microbes.** Новый защищённый серверный запуск нужен для воспроизводимой фиксации текущего состояния repository и результатов, а не для объявления этой проблемы решённой.
